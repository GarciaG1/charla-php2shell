Guía de parcheo · PHP2Shell

CVE-2026-109618 y CVE-2026-109619. Cómo actualizar PHP correctamente en cada sistema operativo y con cada servidor web. Versiones corregidas: 8.5.12 · 8.4.27 · 8.3.36 · 8.2.35. Datos al 28 de octubre de 2026 — confirma siempre el aviso de tu distribución.

0Las reglas que aplican a todos

Antes de ir a tu caso, cuatro cosas que valen para cualquier instalación:

  1. Actualizar el paquete no basta: hay que reiniciar PHP. Los procesos (workers) que ya estaban corriendo siguen con el código viejo en memoria. Si no reinicias PHP-FPM o Apache, el parche no toma efecto.
  2. El número de versión engaña. Ubuntu, Debian y Red Hat corrigen sin cambiar el número (backport). Un 8.3.6 de tu distro puede estar parchado. Valida por el aviso o el changelog del paquete, no por el número.
  3. Cada contenedor trae su propio PHP. Parchar el host no toca el PHP de adentro. Hay que reconstruir la imagen y volver a desplegar.
  4. Primero lo expuesto a internet, hoy. Lo interno, esta semana. Con código de prueba público, el margen es de horas.

Identifica tu caso en dos comandos:

# ¿qué versión y cómo corre PHP?
$ php -v
$ php -i | grep "Server API"     # Apache 2.0 Handler = mod_php · FPM/FastCGI = PHP-FPM · CLI = línea de comandos
Hay un checker read-only incluido en la charla: python revisar_php.py revisa esta máquina, los contenedores corriendo y (con --imagenes) tus imágenes locales. Úsalo antes y después de parchar.

1Por sistema operativo

Actualiza con el gestor de paquetes del sistema. Luego pasa a la sección 2 para reiniciar el servidor web correcto.

Debian · Ubuntu apt

$ sudo apt update
$ sudo apt install --only-upgrade 'php*'      # actualiza PHP y sus módulos
$ php -v                                       # confirma la versión corregida o el backport de Ubuntu/Debian
$ sudo systemctl restart php8.3-fpm            # ajusta a tu versión; y/o apache2 si usas mod_php
¿Usas el PPA de Ondřej Surý para versiones recientes? Asegúrate de que esté al día: sudo add-apt-repository ppa:ondrej/php && sudo apt update. En Debian, el repo packages.sury.org/php.

RHEL · Rocky · AlmaLinux · CentOS Stream dnf

$ sudo dnf upgrade 'php*'
$ sudo dnf module update php                   # si instalaste PHP vía módulos (AppStream)
$ php -v
$ sudo systemctl restart php-fpm httpd
Si usas el repo Remi para versiones nuevas: sudo dnf module reset php y luego sudo dnf module enable php:remi-8.3 antes de actualizar.

Fedora dnf

$ sudo dnf upgrade 'php*'
$ sudo systemctl restart php-fpm

openSUSE · SLES zypper

$ sudo zypper refresh
$ sudo zypper update 'php8*'
$ sudo systemctl restart php-fpm

Arch · Manjaro pacman

$ sudo pacman -Syu php php-fpm
$ sudo systemctl restart php-fpm
Arch siempre trae la última versión: un -Syu completo te deja en la rama corregida. No actualices solo PHP (partial upgrade): actualiza todo el sistema.

Alpine apk común en contenedores

$ apk update
$ apk upgrade php82 php82-fpm              # ajusta a php83/php84 según tu versión
$ rc-service php-fpm82 restart            # o, si es contenedor: reconstruye la imagen

FreeBSD pkg

$ sudo pkg update
$ sudo pkg upgrade php83                   # o vía ports: /usr/ports/lang/php83
$ sudo service php-fpm restart

macOS Homebrew · desarrollo

$ brew update
$ brew upgrade php
$ brew services restart php

Windows desarrollo · IIS

# Desarrollo (winget):
$ winget upgrade --id PHP.PHP.8.3 --exact

# Manual / IIS: descarga el build corregido de windows.php.net (mismo hilo: TS o NTS),
# reemplaza la carpeta de PHP, y recicla el pool de aplicaciones o reinicia IIS:
$ iisreset

2Por servidor web — qué reiniciar

Actualizar el paquete deja el binario nuevo en disco, pero el proceso que atiende peticiones sigue con el código viejo. Esto es lo que hay que reiniciar según cómo corre PHP:

Cómo corre PHPDónde está el PHP que atiendeQué reiniciar
Apache + mod_php riesgo más altoDentro del proceso de ApacheApache completo (restart, no reload)
Apache + PHP-FPMEn el servicio php-fpmphp-fpm; recarga Apache
Nginx + PHP-FPMEn el servicio php-fpmphp-fpm (Nginx solo hace de proxy)
LiteSpeed / OpenLiteSpeedEn los procesos lsphpEl servidor LiteSpeed
Caddy / FrankenPHPphp-fpm, o PHP embebidophp-fpm, o actualizar el binario
IIS + FastCGIProcesos php-cgiReciclar el pool / iisreset

Apache + mod_php el ataque ocurre antes de tu app

$ sudo systemctl restart apache2        # Debian/Ubuntu
$ sudo systemctl restart httpd          # RHEL/Rocky/Alma/Fedora
restart, no reload. Un reload no recarga el módulo de PHP ya cargado en memoria: necesitas reiniciar Apache por completo.

Apache + PHP-FPM

$ sudo systemctl restart php8.3-fpm
$ sudo systemctl reload apache2         # Apache solo pasa la petición al pool de FPM

Nginx + PHP-FPM la mayoría de instalaciones modernas

$ sudo systemctl restart php8.3-fpm     # aquí está el PHP que hay que renovar
$ sudo systemctl reload nginx           # opcional; Nginx no ejecuta PHP, solo lo proxya
Reiniciar solo Nginx no arregla nada: el PHP vive en php-fpm. El paso que importa es restart php-fpm.

LiteSpeed · OpenLiteSpeed lsphp

$ sudo apt install --only-upgrade lsphp83*   # o el gestor de tu panel
$ sudo systemctl restart lsws                 # o: /usr/local/lsws/bin/lswsctrl restart

Caddy php_fastcgi

$ sudo systemctl restart php8.3-fpm     # Caddy proxya a FPM; el fix va en FPM

FrankenPHP PHP embebido en el binario

# FrankenPHP trae PHP DENTRO del binario: reiniciar el servicio no basta.
# Actualiza el binario o la imagen y vuelve a desplegar:
$ docker pull dunglas/frankenphp:latest
$ docker compose up -d --force-recreate

IIS + FastCGI Windows

# Reemplaza los binarios de PHP (ver sección 1 · Windows), luego:
$ iisreset                              # o recicla solo el Application Pool del sitio

3Contenedores y orquestación

No se parcha un contenedor en caliente: se reconstruye con la imagen base corregida y se vuelve a desplegar.

Docker · Docker Compose

# 1) En tu Dockerfile, fija una base corregida:  FROM php:8.3-apache  (o 8.3.36-apache)
$ docker compose build --pull           # --pull trae la última base, no la cacheada
$ docker compose up -d                   # redepliega

# Imagen oficial directa, sin Dockerfile propio:
$ docker pull php:8.3-fpm
$ docker compose up -d --force-recreate
Revisa también imágenes guardadas y sin usar: una base vieja volverá si alguien la vuelve a desplegar. docker images y reconstruye o borra las obsoletas.

Kubernetes

$ kubectl set image deploy/mi-app php=mi-registro/mi-app:php8.3.36
$ kubectl rollout restart deploy/mi-app
$ kubectl rollout status  deploy/mi-app   # espera a que termine el despliegue

Escaneo de imágenes

$ trivy image mi-app:latest              # Aqua Trivy
$ docker scout cves mi-app:latest        # Docker Scout
$ grype mi-app:latest                    # Anchore Grype

4Hosting administrado y paneles

cPanel · WHM

En WHM: EasyApache 4 para actualizar los paquetes de PHP, o MultiPHP Manager para asignar una versión soportada por dominio.

$ sudo yum update ea-php83*              # actualiza los paquetes ea-php de cPanel
$ sudo /scripts/restartsrv_httpd         # reinicia el servicio web de cPanel

Plesk

Tools & Settings → Updates para traer los paquetes corregidos; en PHP Settings asigna una versión soportada por dominio.

$ sudo plesk installer update            # o el autoinstaller interactivo

Hosting compartido

El PHP lo administra el proveedor. En tu panel, elige una rama soportada (8.2+) y pregunta por escrito si ya aplicaron el parche. Si no responden pronto, considera mover el sitio.

Cloud gestionado

  • Azure App Service / AWS Elastic Beanstalk: espera (o fuerza) la plataforma actualizada y redepliega la app.
  • Cloud Run / Lambda / contenedores serverless: reconstruye la imagen con la base corregida y vuelve a desplegar — igual que cualquier contenedor.

5PHP sin soporte: 7.4 · 8.0 · 8.1 sin parches oficiales

Estas ramas ya no reciben versiones nuevas. Hay tres caminos, en orden de preferencia:

  1. Migra a 8.2+ — es la única solución real y sostenible.
  2. Parche de tu distribución o de soporte extendido (ELS): Ubuntu Pro, TuxCare y otros publican backports para versiones viejas. Pregúntales y valida por changelog.
  3. Backport en código fuente: PHP publicó parches mínimos para 7.4/8.0/8.1, pero solo sirven si compilas tu propio PHP. No cuentes con eso para producción.
# ¿mi distro ya aplicó el backport? busca las CVE en el changelog del paquete
$ apt changelog php8.1 | grep -E "CVE-2026-10961[89]"        # Ubuntu/Debian
$ rpm -q --changelog php | grep -E "CVE-2026-10961[89]"      # RHEL/Rocky/Alma

6Si hoy no puedes parchar: mitigación temporal

Esto no sustituye el parche. Cierra caminos de la 109619 (y la 115560). Para la 109618 no hay mitigación confiable: solo actualizar. Es para ganar horas.
# php.ini, o un .ini del pool de PHP-FPM (NO ini_set() ni .user.ini)
session.upload_progress.enabled = 0
fatal_error_backtraces = 0             # solo tiene efecto en PHP 8.5

# y reinicia TODOS los workers
$ sudo systemctl restart php8.3-fpm     # o apache2 / httpd según tu caso
  • No sirve: ocultar errores con display_errors o error_reporting.
  • Dónde va: en php.ini o en el pool de FPM. ini_set() y .user.ini no la aplican a tiempo.
  • Si ni eso puedes hoy: saca el sitio de internet mientras parchas. El FBI recomendó desconectar lo que no se pudiera actualizar de inmediato.

7Verificación — ¿de verdad quedó?

  1. Versión: php -v y, si usas FPM, php-fpm8.3 -v (el binario de FPM es el que atiende).
  2. Si viene de tu distro: confirma por el aviso o el changelog, no por el número (puede estar parchado sin cambiarlo).
  3. Workers reiniciados: que no queden procesos viejos.
  4. Re-escaneo: python revisar_php.py (y --imagenes para tus imágenes Docker).
# ¿quedaron workers con el código viejo? mira cuándo arrancaron
$ ps -eo pid,lstart,cmd | grep -E 'php-fpm|apache2|httpd' | grep -v grep
# la hora de arranque debe ser POSTERIOR a tu reinicio

8¿Y si ya entraron antes de que parcharas?

Parchar detiene el acceso futuro, pero no deshace una intrusión previa. Si había PHP vulnerable expuesto, revisa:

$ ps -eo user,pid,lstart,cmd | grep -E '^(www-data|apache|nginx)'   # procesos del usuario de PHP
$ ss -tnp | grep -i php                                             # conexiones de PHP ahora mismo
$ find /tmp /var/tmp -newer /etc/hostname -type f                   # archivos recientes en temporales

Señales (Sophos): conexiones de PHP que duran de más, procesos con nombres raros o corriendo desde /tmp, tráfico de IPs de mala reputación, errores fatales y reinicios de workers que antes no había. CISA publicó una regla SIGMA para detectar intentos.

Si encuentras indicios: aísla el servidor, conserva los logs, rota credenciales (base de datos, llaves, tokens) y, en la duda, reconstruye desde una imagen limpia. Parchar no basta.

Fuentes: Centro Canadiense de Ciberseguridad, AL26-026 · Datadog Security Labs · Ubuntu · Huntress · Sophos · BleepingComputer. Valida siempre contra el aviso oficial de tu distribución el día que parches.
